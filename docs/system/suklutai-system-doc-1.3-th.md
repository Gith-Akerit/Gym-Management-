# บทที่ 1 · อ่านหน้าเดียวจบ (สำหรับเจ้าของยิม)

หน้านี้เขียนให้คนที่ไม่ได้ทำงานสายคอมพิวเตอร์อ่านจบได้ในสองนาที บทถัดไปเป็นรายละเอียดสำหรับคนที่ต้องลงมือดูแลเครื่อง

<!-- pagebreak -->

## ข้อมูลของลูกค้าอยู่ที่ไหน

อยู่บน **เครื่องเซิร์ฟเวอร์ของยิมเครื่องเดียว** ที่เช่าไว้ (VPS ของ Hostinger) ทั้งหมด — ชื่อ เบอร์ อีเมล รูปถ่าย ประวัติเช็กอิน และประวัติการรับเงิน

**ไม่มีข้อมูลลูกค้าถูกส่งออกไปเก็บที่บริษัทอื่น** ไม่มีบัญชีคลาวด์ของเจ้าอื่นมาเกี่ยวข้อง ระบบส่งข้อมูลออกจากเครื่องอยู่อย่างเดียวคือ **อีเมลที่ส่งถึงลูกค้าและพนักงาน** ซึ่งออกผ่านกล่องจดหมาย Microsoft 365 ของยิมเอง

<!-- pagebreak -->

## ใครเปิดดูได้บ้าง

| ใคร | เห็นอะไร |
|---|---|
| **พนักงาน** (บัญชีที่คุณสร้างให้) | รายชื่อสมาชิก บัตร การเช็กอิน การรับเงิน และแก้ข้อมูลสมาชิกได้ |
| **เจ้าของยิม** | ทุกอย่างของพนักงาน + ตั้งค่ายิม แพ็กเกจ บัญชีผู้ใช้ อีเมลของระบบ และภาพหน้าจอในเรื่องที่พนักงานแจ้ง |
| **สมาชิก** | เฉพาะส่วน "ช่วยเล่น" ของตัวเอง — วิธีใช้เครื่องและโปรแกรมฝึก **ไม่เห็นข้อมูลของสมาชิกคนอื่นเลย** |

## ถ้าเครื่องพัง จะเป็นอย่างไร

ชุดสำรองอยู่บนเครื่องเดียวกัน ดังนั้น **เครื่องพังพร้อมกันทั้งเครื่องคือกรณีที่ยังกู้ไม่ได้** ถ้าไม่มีสำเนาอยู่ที่อื่น — เป็นข้อจำกัดที่ต้องรู้ ไม่ใช่ความลับ

**ทางที่เลือกไว้แล้ว: ก๊อปปี้ชุดสำรองออกนอกเครื่องสัปดาห์ละครั้ง** ด้วยคำสั่งเดียว (`scp`) ลงคอมพิวเตอร์ของยิม — ไม่มีค่าใช้จ่ายเพิ่ม ใช้เวลาไม่กี่นาที ขั้นตอนอยู่ในข้อ 3.5 · **สแนปช็อตของผู้ให้บริการ VPS** เป็นทางเลือกที่สะดวกกว่าแต่มีค่าใช้จ่ายรายเดือน เปิดเพิ่มได้ทีหลังถ้าเปลี่ยนใจ

> ไฟล์สำรองที่ก๊อปปี้ออกมา **มีข้อมูลลูกค้าทั้งยิมและค่าลับของระบบอยู่ในไฟล์เดียว** — เก็บไว้บนเครื่องที่มีรหัสผ่านเปิดเครื่อง อย่าวางไว้ในโฟลเดอร์ที่แชร์กัน และ **อย่าส่งต่อทางแชตหรืออีเมล**

# บทที่ 2 · ข้อมูลส่วนบุคคลของลูกค้า

บทนี้ไล่ทีละประเภทว่า **เก็บอะไร · เก็บไว้ที่ไหน · ใครเปิดดูได้ · เก็บนานแค่ไหน · ลบอย่างไร** ทุกบรรทัดตรวจกับโค้ดของรุ่นที่จะติดตั้งรอบนี้ ไม่ได้เขียนจากความเข้าใจทั่วไป

**ที่อยู่ของทุกอย่าง** เครื่อง VPS ของยิมเครื่องเดียว · ฐานข้อมูล SQLite หนึ่งไฟล์ และโฟลเดอร์ไฟล์แนบ ทั้งคู่อยู่ใน volume ถาวรชื่อ `/data` ของคอนเทนเนอร์แอป · **ไม่มีข้อมูลลูกค้าถูกส่งไปเก็บที่ผู้ให้บริการรายอื่น**

## 2.4 การลบข้อมูล

**สิ่งที่ปุ่มในแอปทำจริง**

- **"ระงับสมาชิก"** = ปิดไม่ให้เข้าใช้ **ไม่ใช่การลบ** — ชื่อ เบอร์ รูป และประวัติยังอยู่ครบ (เจตนา: ประวัติการรับเงินต้องตรวจย้อนได้)
- **ล้างช่องอีเมลในหน้าแก้ไขข้อมูลสมาชิก** = ตัดบัญชีเข้าใช้ "ช่วยเล่น" ออกจากสมาชิกรายนั้น และเตะออกจากระบบทันที
- **"ลบเรื่องนี้"** ในเรื่องที่แจ้ง = ลบทั้งเรื่องและไฟล์ภาพหน้าจอ ย้อนกลับไม่ได้
- **ถ่ายรูปสมาชิกใหม่** = เขียนทับไฟล์รูปเดิม ไฟล์เก่าไม่เหลือ

**ถ้าลูกค้าขอให้ลบข้อมูลทั้งหมดของเขา** ต้องให้ผู้ดูแลเครื่องทำบนเครื่อง ตามลำดับนี้

1. บันทึกคำขอไว้ (วันที่ ใครขอ ใครรับเรื่อง)
2. ลบไฟล์รูปถ่ายของสมาชิกรายนั้นใน `/data/photos` และสลิปที่เป็นของเขาใน `/data/slips`
3. ลบหรือลบชื่อออกจากแถวในฐานข้อมูล — **ต้องตัดสินใจก่อนว่าจะเก็บประวัติการรับเงินแบบไม่ระบุตัวตนไว้หรือไม่** (เอกสารบัญชีของยิมอาจต้องใช้)
4. แจ้งว่า **ชุดสำรองย้อนหลัง 7 วันยังมีข้อมูลนั้นอยู่** จนกว่าจะครบรอบและถูกทับไปเอง

**การลบบัญชีกับบันทึกการกระทำ — เปลี่ยนไปในรุ่น `b8a9d96`** ตาราง `audit_logs` มีคอลัมน์ `actor_id` ที่อ้างถึงตาราง `users` แบบบังคับ (foreign key) เดิมไม่มีกฎ "ลบตาม" เลย ทำให้ลบบัญชีที่เคยทำอะไรไว้ไม่ได้ · **migration 018 แก้เรื่องนี้แล้ว**

- **แถวบันทึกจะอยู่รอดเมื่อบัญชีถูกลบ** ระบบย้ายให้ไปชี้ที่ **บัญชีตัวแทน `deleted-user`** ซึ่งล็อกอินไม่ได้และไม่โผล่ในรายชื่อบัญชี · รายงานแสดงเป็นคำว่า **"บัญชีที่ถูกลบ"** — ประวัติว่าใครแตะข้อมูลของลูกค้าจึงไม่หายไปพร้อมบัญชี
- **แต่ในทางปฏิบัติวันนี้ยังลบบัญชีไหนไม่ได้อยู่ดี** เพราะตารางอื่นยังอ้าง `users` แบบไม่มีกฎ "ลบตาม" โดยเฉพาะ `password_setup_tokens` ซึ่ง**ทุกบัญชีที่สร้างผ่านหน้า "บัญชีผู้ใช้" จะมีแถวอยู่เสมอ** · migration 018 จึงเป็นเกราะที่เตรียมไว้ล่วงหน้า ไม่ใช่ของที่ทำงานอยู่แล้ว (ดูข้อ 4.12.3)
- **วิธีที่ใช้อยู่และปลอดภัยกว่า** คือ **ระงับบัญชี** ซึ่งปิดการเข้าใช้ทันทีและเก็บประวัติไว้ครบ

งานที่เหลือคือ migration 019 ให้ครอบตารางอื่น — อยู่ในรายการงานถัดไปแล้ว (ภาคผนวก ก.6)

> ยังไม่มีปุ่ม "ลบสมาชิกถาวร" ในแอปโดยตั้งใจ เพราะการลบที่กดพลาดแล้วกู้ไม่ได้อยู่ห่างจากปุ่ม "ระงับ" เพียงหนึ่งบรรทัดในตาราง — ถ้าต้องการให้มี ให้สั่งทีมทำเป็นงานแยกพร้อมขั้นตอนยืนยันสองชั้น

## 2.4 (ต่อ) "เก็บ 180 วัน" แปลว่าอะไรจริง ๆ

ถ้าต้องตอบลูกค้าหรือหน่วยงานว่าข้อมูลอยู่ในระบบนานเท่าไร **ต้องนับสามชั้น ไม่ใช่ชั้นเดียว** — ตัวเลขในตารางข้อ 2.1 คือชั้นแรกเท่านั้น

| ชั้น | อยู่ได้นานแค่ไหน |
|---|---|
| **1 · ในระบบที่ใช้งานอยู่** | ตามตารางข้อ 2.1 — ภาพแจ้งปัญหา **180 วัน** · สลิป **365 วัน** · รูปถ่ายสมาชิกและประวัติ **เก็บถาวรจนกว่าจะลบ** |
| **2 · ในชุดสำรองบนเครื่อง** | **ไม่เกิน 7 วันหลังจากนั้น** — ไฟล์สำรองรายวันเก็บย้อนหลัง 7 ชุด ของที่ถูกลบจากระบบวันนี้จึงยังอยู่ในชุดสำรองอีกไม่เกินหนึ่งสัปดาห์แล้วหายไปเอง |
| **3 · ในสำเนานอกเครื่อง** | **ตามรอบที่ยิมก๊อปปี้ออกไปและเก็บไว้เอง** — ระบบตามไปลบให้ไม่ได้ · ถ้าลบข้อมูลของลูกค้ารายหนึ่งแล้ว ต้องตั้งใจลบสำเนาเก่าที่อยู่ในคอมพิวเตอร์ของยิมด้วย |

**คำตอบที่ถูกต้องเมื่อมีคนถาม** คือ *"ในระบบเก็บ (ตามตาราง) · ในชุดสำรองอีกไม่เกิน 7 วัน · และในสำเนาที่ยิมเก็บไว้เองตามรอบที่ยิมกำหนด"* — ถ้าตอบแค่ตัวเลขชั้นแรก จะเป็นคำตอบที่ไม่ตรงกับความจริงของเครื่อง

**ข้อแนะนำเชิงปฏิบัติ** เก็บสำเนานอกเครื่องไว้ **ไม่เกิน 4 ชุดล่าสุด** แล้วลบของเก่าทิ้งเมื่อคัดลอกชุดใหม่ลงไป · จดไว้ว่าเก็บที่เครื่องไหน ใครเปิดได้ เพื่อให้ตอบได้จริงเมื่อถูกถาม

## 2.5 สามเรื่องที่ต้องรู้เกี่ยวกับความเสี่ยงของข้อมูลชุดนี้

1. **ไฟล์สำรองหนึ่งไฟล์ = ข้อมูลลูกค้าทั้งยิม + ค่าลับของระบบ** — สคริปต์สำรองคัดลอกทั้งโฟลเดอร์ `/data` และ **สำเนาของ `.env`** (ซึ่งมีทั้งกุญแจเซ็นบัตรและกุญแจถอดรหัสกล่องจดหมาย) ไว้ในไฟล์เดียวกัน · บนเครื่องไฟล์นี้เปิดอ่านได้เฉพาะ root · **สำเนาที่ก๊อปปี้ออกไปต้องถือว่าเป็นของลับระดับสูงสุดของยิม** เก็บบนเครื่องที่มีรหัสผ่าน ไม่ส่งต่อทางแชต · การมี `.env` อยู่ในไฟล์สำรองเป็นเรื่องจำเป็น ไม่ใช่ความสะเพร่า — ถ้าไม่มี กู้เครื่องแล้วบัตรสมาชิกทุกใบจะใช้ไม่ได้
2. **ชุดสำรองเก็บบนเครื่องเดียวกับข้อมูลจริง** จึงกันได้เฉพาะ "ลบผิด/ข้อมูลเสีย" ไม่ได้กันเครื่องหายทั้งเครื่อง — ทางที่เลือกไว้คือก๊อปปี้ออกนอกเครื่องสัปดาห์ละครั้ง (บทที่ 1 และข้อ 3.5)
3. **บันทึกการเข้าเว็บของ Caddy ไม่ได้อยู่ในชุดสำรองและไม่ได้ถูกลบตามนโยบายข้อมูลลูกค้า** — มันหมุนทับตัวเองตามขนาดไฟล์ ไม่ใช่ตามอายุ · ถ้าต้องการให้ครบตามนโยบาย ให้ตั้งอายุการเก็บของไฟล์นี้เพิ่มในบทที่ 3

| | เวอร์ชัน / อิมเมจ | หน้าที่ |

**`app` ไม่ได้เปิดพอร์ตออกอินเทอร์เน็ตเลย** — เข้าถึงได้ทางเดียวคือผ่าน Caddy นี่คือขอบเขตความปลอดภัยชั้นแรกของระบบ

ไฟล์ตั้งค่าของ Caddy อยู่ที่ `deploy/Caddyfile` เนื้อหาโดยสรุป:

```
{$APP_DOMAIN} {
    encode gzip
    reverse_proxy app:3000 {
        header_up X-Forwarded-For {remote_host}
        header_up X-Forwarded-Proto {scheme}
    }
    log { output file /data/access.log { roll_size 10MiB  roll_keep 5 } }
}
```

**HTTPS อัตโนมัติ** Caddy ขอใบรับรองจาก Let's Encrypt เองและต่ออายุเองก่อนหมดอายุ ไม่ต้องมีใครจำวันหมดอายุ
ใบปัจจุบัน: `CN=srv1979069.hstgr.cloud` ออกโดย Let's Encrypt ใช้ได้ถึง **13 ธันวาคม 2569**
เงื่อนไขที่ทำให้ต่ออายุสำเร็จคือ DNS ของ `srv1979069.hstgr.cloud` ต้องชี้มาที่เครื่องนี้ และพอร์ต 80/443 ต้องเปิดอยู่ — ถ้าวันหนึ่งใบรับรองหมดอายุ ให้ตรวจสองข้อนี้ก่อนเสมอ

`X-Forwarded-For` ที่ Caddy ใส่ให้ คู่กับ `TRUST_PROXY=1` ฝั่งแอป คือสิ่งที่ทำให้ระบบรู้ IP จริงของผู้ใช้
ถ้าตั้งผิด ผู้ใช้ทุกคนจะถูกนับรวมเป็นคนเดียวในระบบจำกัดจำนวนครั้ง แล้วล็อกทั้งยิมออกจากระบบพร้อมกัน

### 3.4 (ต่อ) คีย์ที่ต้องระวังเป็นพิเศษ

**เรื่อง `CARD_SIGNING_SECRET`** ลายเซ็นบน QR ของบัตรสมาชิกทุกใบผูกกับค่านี้ ถ้าเปลี่ยนเมื่อไร **บัตรที่แจกไปแล้วทุกใบจะสแกนไม่ผ่านพร้อมกัน เงียบ ๆ ไม่มีข้อความบอกสาเหตุ** ทางกู้คืนมีทางเดียวคือเอาค่าเดิมกลับมา หรือออกบัตรใหม่ให้สมาชิกทุกคน — นี่คือเหตุผลที่ขั้นตอนกู้คืนข้อมูลต้องคืน `.env` ก่อนเสมอ

**เรื่อง `PILOT_MODE`** ถ้าเคลียร์ค่านี้ทิ้งขณะที่ยังไม่มี `PROMPTPAY_ID` **แอปจะไม่ยอมบูตและเว็บล่มทันที** (เป็นพฤติกรรมที่ตั้งใจ กันเปิดรับเงินโดยไม่มีบัญชีรับเงิน) เส้นทางเปิดใช้จริงที่ถูกต้องคือรัน `deploy/bootstrap.sh` **โดยไม่ใส่ `--pilot`** ซึ่งจะถาม PromptPay ID แล้วตั้งค่าให้เองอย่างถูกลำดับ

**หมายเหตุสำคัญเรื่องพาธ** `docker-compose.yml` กำหนด `DATABASE_PATH`, `SLIP_STORAGE_PATH`, `PHOTO_STORAGE_PATH`, `LOGO_STORAGE_PATH`, `REPORT_STORAGE_PATH` ไว้ในส่วน `environment:` ซึ่ง**ทับค่าจาก `.env` เสมอ** การแก้พาธเหล่านี้ใน `.env` จึงไม่มีผลใด ๆ ถ้าต้องเปลี่ยนจริงต้องแก้ที่ `docker-compose.yml`

**สองกับดักของ `.env` ที่เจอมาแล้วบนเครื่องจริง**

1. **แก้ `.env` ก่อนรัน `up.sh` เสมอ ไม่ใช่หลัง** — คอนเทนเนอร์อ่านไฟล์นี้ตอน**สร้าง**เท่านั้น ตั้งคีย์ใหม่หลัง `up.sh` แล้วแอปจะยังไม่เห็นค่านั้นจนกว่าจะสร้างคอนเทนเนอร์ใหม่อีกรอบ
2. **ห้ามรัน `docker compose exec app npm run env:set`** — `env-set.js` หาไฟล์ `.env` เทียบกับโฟลเดอร์ปัจจุบัน ซึ่งในคอนเทนเนอร์คือ `/app` ไม่ใช่ `/srv/gym` · ผลคือเขียนไฟล์ใหม่ลงใน layer ของอิมเมจ **ซึ่งหายไปตอน rebuild โดยไม่มี error** ให้รันบนตัวเครื่องที่ `/srv/gym` ในฐานะ root หรือในคอนเทนเนอร์ชั่วคราวที่ mount `/srv/gym` เข้ามาแล้วชี้ `ENV_FILE` มาที่นั่น

**วิธีแก้ค่าใน `.env` อย่างปลอดภัย** ใช้สคริปต์ของระบบ ไม่ต้องเปิดไฟล์แก้มือ — มันเขียนทับเฉพาะบรรทัดที่ระบุ เขียนแบบ atomic และไม่พิมพ์ค่ากลับออกมา:

```bash
cd /srv/gym
npm run env:set -- KEY=VALUE
npm run env:set -- --stdin KEY     # พิมพ์ค่าแล้ว Enter ค่าจะไม่ปรากฏในบรรทัดคำสั่งและไม่ลง history
npm run env:set -- --list          # ดูว่ามีคีย์อะไรบ้าง โดยไม่แสดงค่า
```

> **แท็บ "อีเมลของระบบ" อยู่ในรุ่น `b8a9d96` แล้ว** เจ้าของยิมกรอกรหัสกล่องจดหมายเองผ่านหน้าเว็บ ระบบเก็บเข้ารหัสไว้ในฐานข้อมูลด้วยคีย์ `SETTINGS_ENC_KEY` ในตารางด้านบน — ค่ารหัสไม่เคยอยู่ใน `.env` และไม่มีหน้าจอไหนแสดงกลับ

### ข้อจำกัดที่ต้องรู้ และการก๊อปปี้ออกนอกเครื่อง

**เจ้าของยิมตัดสินใจแล้วว่าจะก๊อปปี้ออกนอกเครื่อง สัปดาห์ละหนึ่งครั้ง** ลงคอมพิวเตอร์ของยิม (ไม่มีค่าใช้จ่ายเพิ่ม) ทำจากเครื่องที่มีกุญแจ SSH ด้วยคำสั่งเดียว:

```bash
scp -i <กุญแจ> root@187.127.107.148:/var/backups/gym/gym-*.tar.gz ./
```

ไฟล์ที่ได้ **มีข้อมูลลูกค้าทั้งยิมและสำเนา `.env`** เก็บไว้บนเครื่องที่มีรหัสผ่านเปิดเครื่อง อย่าวางในโฟลเดอร์ที่แชร์กัน และ **อย่าส่งต่อทางแชตหรืออีเมล** · ทางเลือกที่สะดวกกว่าแต่มีค่าใช้จ่ายรายเดือนคือเปิด snapshot/backup ของ Hostinger เพิ่มอีกชั้น

### ขั้นตอนกู้คืน

```bash
cd /srv/gym
mkdir -p /tmp/restore && tar xzf /var/backups/gym/gym-<วันเวลา>.tar.gz -C /tmp/restore
git fetch origin release/pilot
```

และต้อง checkout โค้ดตาม `./revision` ด้วย เพราะข้อมูลที่กู้มาอาจมีโครงสร้างตรงกับโค้ดรุ่นนั้นเท่านั้น

## 3.6 พอร์ตและไฟร์วอลล์

ไฟร์วอลล์คือ `ufw` สถานะ **active** นโยบาย **ปฏิเสธขาเข้าทั้งหมดโดยปริยาย อนุญาตขาออกทั้งหมด**

| พอร์ต | ใช้ทำอะไร |
|---|---|
| `22/tcp` | SSH (กุญแจเท่านั้น) |
| `80/tcp` | HTTP — ใช้เปลี่ยนเส้นทางไป HTTPS และให้ Let's Encrypt ตรวจสิทธิ์โดเมน **ห้ามปิด** ไม่งั้นใบรับรองต่ออายุไม่ได้ |
| `443/tcp` | HTTPS |

เปิดครบทั้ง IPv4 และ IPv6 · ไม่มีพอร์ตอื่นเปิดออกอินเทอร์เน็ต · ฐานข้อมูลไม่ได้เปิดพอร์ตใด ๆ เพราะเป็น SQLite ที่เป็นไฟล์ในคอนเทนเนอร์

> **ข้อควรระวัง** พอร์ตที่ Docker เปิดเอง (`ports:` ใน compose) **ข้าม ufw ได้** ปัจจุบันโปรเจกต์นี้เปิดแค่ 80/443 ของ Caddy ซึ่งตั้งใจให้เปิดอยู่แล้ว
> อย่านำคอนเทนเนอร์อื่นที่มี `ports:` มารันบนเครื่องนี้ เพราะจะเปิดพอร์ตออกอินเทอร์เน็ตโดยที่ `ufw status` ไม่แสดงให้เห็น

การเชื่อมต่อขาออกที่ระบบต้องใช้: `443` (Let's Encrypt, GitHub) และ `587` (ส่งอีเมลผ่าน Office 365 เมื่อเปิดใช้) — ทดสอบแล้วว่าต่อ `smtp.office365.com:587` พร้อม STARTTLS ได้จากเครื่องนี้

## 3.7 ขั้นตอนอัปเดตรุ่น

```bash
cd /srv/gym
bash deploy/backup.sh                                     # สำรองก่อนเสมอ (แอปหยุดราว 1 วินาที)
git fetch origin release/pilot
git checkout -f --detach <COMMIT SHA เต็ม>
./deploy/up.sh --wait --wait-timeout 180
```

**ต้องใช้ `./deploy/up.sh` ไม่ใช่ `docker compose up` ตรง ๆ** เพราะสคริปต์อ่านเลข commit จาก git แล้วส่งเข้าไปฝังในหน้าเว็บเป็น `APP_REVISION` ใบแจ้งปัญหาที่พนักงานส่งจึงติดเลขรุ่นมาด้วย ถ้า build ด้วย compose ตรง ๆ ช่องนั้นจะว่าง และรายงานที่มาถึงหลังอัปเดตรุ่นถัดไปจะไม่มีใครรู้ว่าพูดถึงหน้าจอรุ่นไหน

**อย่าสั่ง `chmod +x deploy/up.sh`** ถ้าเจอ Permission denied ให้ใช้ `sh deploy/up.sh` แทน — การ chmod เป็นการแก้ mode ของไฟล์ที่ git ติดตามอยู่ สคริปต์จะมองว่า working tree สกปรกแล้วประทับเลขรุ่นเป็น `<sha>-dirty` ทั้งที่โค้ดตรงกับ commit ทุกบรรทัด (ตั้งแต่รุ่น `ecb2a5d` สิทธิ์ไฟล์ถูกแก้ใน repo แล้ว จึงไม่ต้อง chmod อีก)

**ตรวจหลังอัปเดตทุกครั้ง**

1. บรรทัด `{"event":"deploy_build","app_revision":"..."}` ต้องไม่ลงท้าย `-dirty`
2. `curl -s https://srv1979069.hstgr.cloud/api/health` ต้องได้ `{"status":"ok"}`
3. `docker compose ps` ต้อง healthy ทั้งสองคอนเทนเนอร์
4. เลข migration ตรงกับที่รุ่นนั้นระบุ และ `pragma foreign_key_check` ต้องว่าง
5. บัญชีผู้ดูแลยังอยู่ครบ
6. ถ้ารอบนั้นแก้หน้าตา ให้ดึง stylesheet ที่เสิร์ฟจริงมาตรวจ ไม่ใช่ดูแค่ในโค้ด

**ย้อนรุ่น** `git checkout -f --detach <SHA เดิม>` แล้ว `./deploy/up.sh` — กู้ฐานข้อมูลด้วยเฉพาะเมื่อรุ่นนั้นมี migration

**ถ้า build ล้มเหลว ให้ดู `.dockerignore` เป็นที่แรก** เคยเกิดสองครั้งและทั้งสองครั้งไม่ใช่ความผิดของ `Dockerfile`: ครั้งแรกโฟลเดอร์ `shared/` ไม่ได้ถูก COPY ครั้งที่สอง `.dockerignore` กัน `docs` ไว้จนคู่มือ PDF ไม่เข้า build context · ไม่มีเทสต์ไหนจับได้เพราะไม่มีชุดไหนรัน `docker build` ปัจจุบันมีเทสต์ `tests/dockerfile-copies.test.js` คอยจับแล้ว

## 3.8 ขั้นตอนย้ายไปเครื่องใหม่

ใช้เมื่อเปลี่ยนผู้ให้บริการ อัปเกรดเครื่อง หรือกู้จากเครื่องที่พังทั้งเครื่อง

**ก่อนเริ่ม** เตรียม 3 อย่าง: ไฟล์สำรองล่าสุด (`gym-*.tar.gz`), สิทธิ์แก้ DNS ของโดเมน, และ SSH public key ที่จะใช้กับเครื่องใหม่

1. **เครื่องใหม่** สั่ง VPS สเปคเท่าเดิมหรือสูงกว่า ระบบปฏิบัติการ **Ubuntu 22.04 / 24.04 / 26.04** (ตัวติดตั้งรับเฉพาะสามรุ่นนี้) และต้องเป็นเครื่องเปล่าที่ไม่มีบริการอื่นรันอยู่
2. **ติดตั้ง** รันคำสั่งติดตั้งชุดเดียวกับที่ใช้ตอนแรก โดย pin commit เดียวกับที่อยู่ในไฟล์ `./revision` ของชุดสำรอง — ตัวติดตั้งจะลง Docker, ตั้ง ufw, ตั้ง cron และสร้าง `.env` ใหม่ให้
3. **คืนข้อมูล** ทำตามขั้นตอนกู้คืนในข้อ 3.5 — **ใช้ `.env` จากไฟล์สำรอง ไม่ใช่ `.env` ที่ตัวติดตั้งเพิ่งสร้าง** เพราะต้องได้ `CARD_SIGNING_SECRET` ตัวเดิมกลับมา ไม่อย่างนั้นบัตรสมาชิกที่แจกไปแล้วใช้ไม่ได้ทั้งหมด
4. **ย้ายโดเมน** ชี้ DNS ของ `srv1979069.hstgr.cloud` (หรือโดเมนใหม่) มาที่ IP ใหม่ ถ้าเปลี่ยนชื่อโดเมนต้องแก้ `APP_DOMAIN` และ `APP_ORIGIN` ให้ตรงกันทั้งคู่ · รอ Caddy ขอใบรับรองใหม่ (ไม่กี่นาที) แล้วตรวจ `https://<โดเมน>/api/health`
5. **ปิดเครื่องเก่า** ต่อเมื่อเครื่องใหม่ผ่านครบ: health 200, ล็อกอินได้, สแกนบัตรใบเดิมของสมาชิกผ่าน, รูปสมาชิกและโลโก้ขึ้นครบ · **การสแกนบัตรใบเดิมได้คือข้อพิสูจน์ว่า `CARD_SIGNING_SECRET` ถูกคืนถูกต้อง** ควรทดสอบก่อนปิดเครื่องเก่าเสมอ

## 4.3 ฐานข้อมูล

ไฟล์เดียว SQLite ที่ `DATABASE_PATH` (บนเครื่องจริง `/data/gym.sqlite`) · เปิดแบบ **WAL** และบังคับ `foreign_keys=ON` · ทุกตารางเป็น **STRICT** คือ SQLite ตรวจชนิดข้อมูลให้จริง ไม่ใช่รับอะไรก็ได้

## 4.4 ที่เก็บไฟล์และอายุการเก็บ

ไฟล์ทุกประเภท**ไม่ได้อยู่ในฐานข้อมูล** — ฐานข้อมูลเก็บแค่ชื่อไฟล์ · ทุกโฟลเดอร์อยู่ใต้ volume `/data` ซึ่งเป็นที่เดียวที่รอดจากการ deploy รอบถัดไปและเป็นที่เดียวที่ backup คัดลอก

| ประเภท | ตัวแปร | ที่เก็บจริง | ใครเปิดดูได้ | อายุการเก็บ |
|---|---|---|---|---|
| **รูปถ่ายสมาชิก** | `PHOTO_STORAGE_PATH` | `/data/photos` | พนักงานและเจ้าของที่ล็อกอิน · **การเปิดดูถูกบันทึก audit** | เก็บตลอดอายุสมาชิก ไม่มีการลบอัตโนมัติ |
| **สลิปโอนเงิน** | `SLIP_STORAGE_PATH` | `/data/slips` | เจ้าของยิม | **365 วัน** (`SLIP_RETENTION_DAYS`) ลบด้วย `npm run slips:prune` |
| **ภาพแจ้งปัญหา** | `REPORT_STORAGE_PATH` | `/data/reports` | **เจ้าของยิมเท่านั้น** และบันทึก audit ทุกครั้งที่เปิด | **180 วัน** (`REPORT_RETENTION_DAYS`) ลบด้วย `npm run reports:prune` |
| **โลโก้ยิม** | `LOGO_STORAGE_PATH` | `/data/logo` | ทุกคน (อยู่บนหน้าเข้าสู่ระบบ) | ไม่ลบ |
| **รูปเครื่องออกกำลังกาย** | `MACHINE_STORAGE_PATH` | `/data/machines` | ทุกคน (อยู่บนหน้าที่เปิดจาก QR ติดเครื่อง) | ไม่ลบ |
| **ฐานข้อมูล** | `DATABASE_PATH` | `/data/gym.sqlite` | ไม่มีใครเปิดตรง ๆ ผ่านเว็บได้ | ไม่ลบ |

**รูปถ่ายสมาชิกกับภาพแจ้งปัญหาเป็นข้อมูลส่วนบุคคล** ส่วนโลโก้กับรูปเครื่องไม่ใช่ จึงแยกโฟลเดอร์กัน — การให้สิทธิ์เข้าโฟลเดอร์รูปเครื่องจะได้ไม่พาสิทธิ์เข้าโฟลเดอร์รูปหน้าคนไปด้วย

มีเทสต์ `tests/deploy-paths.test.js` ที่**อ่านโค้ดเซิร์ฟเวอร์** ว่าใช้ `*_STORAGE_PATH` ตัวไหนบ้าง แล้วบังคับว่าไฟล์ deploy ทั้งสาม (compose/fly/render) ต้องตั้งครบทุกตัวใต้ `/data` และ `entrypoint.sh` ต้อง `mkdir` ให้ — **โฟลเดอร์ที่เพิ่มเดือนหน้าจึงถูกครอบตั้งแต่วันที่เพิ่ม** ไม่ต้องมีใครจำได้

### 4.5.3 สิ่งที่บังคับกับทุกคำขอ

- **CORS/CSRF**: คำขอที่เปลี่ยนข้อมูล (ไม่ใช่ GET/HEAD) ต้องมี header `X-Gym-Client` และ `Origin` ต้องตรงกับ `APP_ORIGIN`
- **`Cache-Control: no-store`** ทุก response ใต้ `/api`
- **CSP** จาก helmet · `img-src` เปิดให้ `blob:` (พรีวิวรูปถ่าย) และ `i.ytimg.com` (ภาพนิ่งคลิป) · `frame-src` เปิดให้ `youtube-nocookie.com` เท่านั้น · **ไม่มี inline script ที่ไหนเลย**
- **rate limit** ต่อ IP และต่อบัญชี ดูตารางข้อ 4.6.4

## 4.6 การเข้ารหัส แฮช ลายเซ็น และ token

### 4.6.1 รหัสผ่าน

**bcrypt cost 12** (`bcryptjs`) ประมาณหนึ่งในสี่วินาทีต่อครั้งบนเครื่องนี้ · ใช้ JS ล้วนโดยตั้งใจ ไม่ใช่ native module เพราะ **การอัปเกรด Node แล้ว native module คอมไพล์ไม่ผ่าน = ไม่มีใครล็อกอินได้ทั้งยิม** ซึ่งเป็นราคาที่แพงกว่าความเร็วที่ได้

การตรวจรหัสผ่าน**ใช้เวลาเท่ากันเสมอ** แม้ไม่มีบัญชีนั้นอยู่จริง — ถ้าตอบเร็วกว่าเมื่อไม่มีบัญชี คนภายนอกจะไล่หาได้ว่าอีเมลไหนมีอยู่ในระบบ

### 4.6.2 รหัสกล่องจดหมายของยิม

**AES-256-GCM** (`server/secret-box.js`) เก็บในคอลัมน์ `mail_settings.password_sealed` รูปแบบ `v1.<iv>.<tag>.<ciphertext>`

**คีย์อยู่ใน `.env` ไม่ได้อยู่ในฐานข้อมูล** — ไฟล์ `.sqlite` ที่หลุดออกไปเดี่ยว ๆ จึงเป็นไฟล์ที่หลุด ไม่ใช่กล่องจดหมายที่หลุด · **ข้อยกเว้นที่ต้องรู้: ชุดสำรองรายวันคัดลอก `.env` ไปไว้ในไฟล์เดียวกับฐานข้อมูล** (ดูข้อ 3.5 และ 2.5) ไฟล์สำรองหนึ่งไฟล์จึงมีทั้งข้อมูลและกุญแจ — จำเป็นต่อการกู้คืน แต่แปลว่าไฟล์สำรองต้องถูกเก็บอย่างของลับ

**ไม่มี route ใดในระบบคืนรหัสนี้กลับมา** ไม่ว่าในรูปแบบไหน · หน้าจอเห็นแค่ "ตั้งค่าไว้แล้ว" และไม่อยู่ใน audit log ด้วย

### 4.6.3 token ทุกชนิดและอายุ

| token | ใช้ทำอะไร | อายุ | เก็บอย่างไร |
|---|---|---|---|
| **session** | ล็อกอินพนักงาน/เจ้าของ | **12 ชั่วโมง** | ตาราง `sessions` เก็บ **SHA-256 ของ token** ไม่ใช่ตัว token · cookie `httpOnly` `sameSite=strict` `path=/api` |
| **session สมาชิก** | ล็อกอินพอร์ทัล | **12 ชั่วโมง** | เหมือนกัน |
| `setup` | ลิงก์ตั้งรหัสผ่านที่เจ้าของยิมสร้างให้ หรือออกจากเครื่อง | **24 ชั่วโมง** | `password_setup_tokens` เก็บ **SHA-256** · ใช้ได้ครั้งเดียว |
| `reset` | ลิงก์ "ลืมรหัสผ่าน" | **30 นาที** | เหมือนกัน — สั้นเพราะคนที่ขอกำลังรออยู่หน้าจอ |
| `verify` | ยืนยันอีเมลตอนสมัครเอง | **24 ชั่วโมง** | เหมือนกัน |
| `member` | ลิงก์ตั้งรหัสผ่านที่ไปกับบัตรสมาชิก | **7 วัน** | เหมือนกัน — ยาวเพราะมาถึงตอนลูกค้ากำลังเดินออกจากยิม |
| `member` (ออกที่เคาน์เตอร์) | ปุ่ม "สร้างลิงก์เข้าช่วยเล่น" บนหน้าบัตร | **24 ชั่วโมง** | ใช้ครั้งเดียว · เขียน audit `member.portal_link_issued` ว่าใครออกให้ใคร · จำกัด 10 ครั้ง/ชม./สมาชิก |
| **ลายเซ็นบัตร** | QR บนบัตรสมาชิก | **ไม่หมดอายุ** | ดูข้อ 4.6.5 |
| token บัตรชั่วคราว | ลิงก์ดาวน์โหลดบัตร 7 วัน | 7 วัน | `check_in_tokens` ลบอัตโนมัติหลังหมดอายุ 7 วัน |

**token หนึ่งใบทำได้อย่างเดียว** — ลิงก์ที่ยืนยันอีเมลตั้งรหัสผ่านไม่ได้ และกลับกัน · การขอลิงก์ชนิดหนึ่งไม่ฆ่าลิงก์อีกชนิดที่ยังอยู่ในกล่องจดหมายเดียวกัน

### 4.6.4 การจำกัดจำนวนครั้ง

| เรื่อง | จำกัด |

| เปลี่ยนรหัสผ่านตัวเอง | 10 ครั้ง / 15 นาที |

### 4.6.5 ลายเซ็นบัตรสมาชิก — ข้อที่ต้องระวังที่สุด

QR บนบัตรคือ `gym1.<รหัสสมาชิก>.<เลขที่บัตร>.<ลายเซ็น>` โดยลายเซ็นเป็น **HMAC-SHA256** ด้วยคีย์ `CARD_SIGNING_SECRET` · การตรวจใช้ `timingSafeEqual` เพื่อไม่ให้หาลายเซ็นถูกได้ด้วยการจับเวลาคำตอบ

**บัตรไม่มีวันหมดอายุ และไม่มีรายการบัตรที่ถูกยกเลิก** — การยกเลิกบัตรทำโดย**นับเลขที่บัตรขึ้นหนึ่ง** ใบเก่าจึงมีลายเซ็นที่ไม่ตรงกับเลขปัจจุบันทันที ไม่ต้องไปตามเก็บบัตรที่ส่งออกไปแล้ว

> ⚠️ **`CARD_SIGNING_SECRET` ห้ามเปลี่ยนเด็ดขาด** · เปลี่ยนเมื่อไหร่ **บัตรทุกใบที่ลูกค้าถืออยู่สแกนไม่ติดพร้อมกันทั้งยิม** และทุกคนถูกออกจากระบบ · กู้ไม่ได้ ต้องออกบัตรใหม่ให้สมาชิกทุกคน · คีย์นี้ต้องยกไปด้วยเมื่อย้ายเครื่อง

### 4.6.6 การป้องกันการไล่หาว่าใครมีบัญชี

สามหน้าจอตอบ**ประโยคเดียวกันทุกกรณี**: เข้าสู่ระบบ · ลืมรหัสผ่าน · เข้าสู่ระบบสมาชิก

- ลืมรหัสผ่านด้วยอีเมลที่ไม่มีบัญชี — **ไม่มีจดหมายออกไปเลยสักฉบับ** และใช้เวลาเท่ากับกรณีที่มีบัญชี (ระบบสร้าง token แล้วทิ้ง เพื่อให้เวลาตอบเท่ากัน)
- หน้าเข้าสู่ระบบสมาชิก ตอบเหมือนเดิมแม้อีเมลนั้นเป็นของพนักงานจริง ๆ — ไม่งั้นหน้านี้กลายเป็นรายการว่าอีเมลไหนทำงานที่ยิม บนหน้าที่ไม่ต้องล็อกอิน
- **หน้าลืมรหัสผ่านฝั่งสาธารณะไม่เคยแสดงลิงก์บนจอ** ไม่ว่าใครกด

## 4.7 การส่งอีเมล

ส่งผ่าน **SMTP ของกล่อง Office 365 ของยิมเอง** — `smtp.office365.com` พอร์ต **587** STARTTLS · ไม่มีผู้ให้บริการภายนอก ไม่มีค่าใช้จ่ายเพิ่ม และผู้รับเห็นอีเมลที่เขารู้จัก

**ค่าตั้งอยู่ในฐานข้อมูล ไม่ใช่ `.env`** เพราะคนที่รู้รหัสกล่องจดหมายคือเจ้าของยิม และหน้าจอเดียวที่เขาเข้าถึงได้คือแอป · กรอกที่ **ตั้งค่ายิม → แท็บ "อีเมลของระบบ"** (เฉพาะเจ้าของยิม)

- **`requireTLS`** เปิดอยู่ — ถ้าเซิร์ฟเวอร์ไม่ยอมเข้ารหัส ระบบ**ตัดการเชื่อมต่อทิ้งโดยไม่ส่งรหัสผ่านออกไป** ส่งไม่สำเร็จดีกว่าส่งรหัสกล่องจดหมายแบบอ่านได้
- **คิวส่งเว้นระยะ ~2 วินาทีต่อฉบับ** เพราะ Office 365 รับราว 30 ฉบับ/นาที/กล่อง
- **log บันทึกแค่ปลายทางและหัวเรื่อง ไม่เคยบันทึกเนื้อจดหมาย** เพราะในนั้นมีลิงก์ที่ใช้ได้จริง — ลิงก์ใน log คือลิงก์ที่คนอ่าน log ใช้ได้
- ยังไม่ได้ตั้งค่า = ระบบทำงานปกติทุกอย่าง แค่ไม่มีจดหมายออก

จดหมาย 5 ฉบับ (`server/emails/`) สร้างจากไฟล์ต้นทางเดียว `mkmail.cjs` ทั้ง HTML และข้อความล้วน — เพื่อไม่ให้สองฉบับพูดคนละเรื่อง · ทุกฉบับ**ไม่มีรูป ไม่มีสคริปต์ ไม่มี List-Unsubscribe** (เป็นจดหมายธุรกรรม) และสีปุ่มมาจากสีของยิมเอง

ความล้มเหลวถูกแปลเป็น 4 กลุ่มที่เจ้าของยิมทำตามได้: **ยังไม่เปิด Authenticated SMTP** · **รหัสผ่านใช้ไม่ได้ (ต้องใช้ App password)** · **เซิร์ฟเวอร์ไม่รองรับการเข้ารหัส** · **ต่อไม่ได้** — บวกกรณีไม่รู้จักที่ยังบอกว่าให้กดแจ้งปัญหา · สองกลุ่มแรกมาจาก Microsoft เป็น `535` เหมือนกันทั้งคู่ แต่วิธีแก้คนละเรื่อง การอ่านรวมกันคือการส่งเจ้าของยิมไปพิมพ์รหัสผ่านใหม่ทั้งที่ไม่ใช่ปัญหา

## 4.9 รันบนเครื่องพัฒนา

ต้องมี **Node 24** เท่านั้น ไม่ต้องมีฐานข้อมูลหรือ Docker

```bash
npm ci
cp .env.example .env          # แล้วเติม CARD_SIGNING_SECRET กับ SETTINGS_ENC_KEY
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"   # ใช้สร้างคีย์ทั้งสอง

npm run db:migrate            # สร้างตารางทั้งหมด
npm run db:seed               # ข้อมูลยิมตั้งต้นและแพ็กเกจร่าง
npm run content:import        # เนื้อหาพอร์ทัลสมาชิก
npm run db:admin              # สร้างบัญชีผู้ดูแลจาก ADMIN_EMAIL/ADMIN_PASSWORD ใน .env

npm run dev                   # หน้าเว็บ (Vite) ที่ http://127.0.0.1:5173
npm start                     # เซิร์ฟเวอร์ที่ http://127.0.0.1:3000
```

ก่อนส่งงานทุกครั้ง:

```bash
npm test                      # 276 ข้อ
npm run build                 # ต้องผ่านก่อนรันเทสต์เบราว์เซอร์
node tests/free-port.js && npx playwright test    # 119 ข้อ
```

คำสั่งอื่นที่มี: `npm run admin:set-password-link -- <email>` (ทางเข้าสำรองเมื่อยังส่งเมลไม่ได้) · `npm run env:set -- --list` (ดูว่ามีคีย์อะไรบ้างโดยไม่แสดงค่า) · `npm run mail:build` (สร้างเทมเพลตจดหมายใหม่จาก `mkmail.cjs`)

## 4.10 สิ่งที่ต้องรู้ก่อนแตะระบบนี้

สามข้อที่ราคาแพงที่สุดถ้าพลาด:

## 4.11 บทเรียนจากการจับภาพหน้าจอ (BUG-14 ถึง BUG-17)

ปุ่ม "แจ้งปัญหา" จับภาพหน้าจอก่อนเปิดกล่องเสมอ · เส้นทางนี้พังสี่แบบในรอบเดียว ทุกแบบเจอจากการทดลองใช้จริงและแก้ไปแล้ว

| # | อาการ | รากของปัญหา | สิ่งที่ทำ |
|---|---|---|---|
| **14** | จอสแกนค้างที่ "กำลังจับภาพหน้าจอ…" เป็นนาที กดอะไรไม่ได้ | ลูปอ่าน QR กับตัวจับภาพแย่ง main thread กันจนภาพไม่เสร็จ | **หยุดถอดรหัส QR ชั่วคราวระหว่างจับภาพ** (กล้องยังเปิด) · **timeout 8 วินาทีวางไว้ในฟังก์ชัน** เพื่อให้ `finally` คืน `<video>` เสมอ · เพิ่มปุ่ม **"ยกเลิก"** ในแผง · แต่ละครั้งที่กดมีเลขกำกับ กล่องที่ถูกยกเลิกแล้วจึงเด้งขึ้นทีหลังไม่ได้ |

| **16** | จับภาพ **ครั้งแรกของหน้า** ช้ากว่าครั้งถัดไปมากจนเกือบชน timeout | โมดูลจับภาพถูกโหลดตอนกดปุ่ม | **โหลดล่วงหน้าตอนว่าง** หลังคนล็อกอินและแอปเคาน์เตอร์ขึ้นแล้ว (`requestIdleCallback` + ตัวสำรอง) · **ไม่โหลดในพอร์ทัลของสมาชิก** ซึ่งไม่มีปุ่มแจ้งปัญหาให้ใช้ |
| **17** | ทุกภาพที่ส่งมามีแผง "กำลังจับภาพหน้าจอ…" บังสิ่งที่กำลังจะรายงาน | แผงอยู่บนจอขณะชัตเตอร์เปิด | **ตัดโหนดที่ติดป้าย `data-capture-hide` ออกจากภาพ** |

**ผลบนเครื่องจริงหลังแก้ครบ** จับภาพได้ทุกครั้ง ครั้งแรก 1.82 วินาที ครั้งถัดไป 1.81 วินาที และภาพไม่มีแผงติดไปด้วย

> **ถ้าต้องแตะส่วนนี้อีก** กฎสามข้อ: ธงหยุดอ่านต้องถูกคืนใน `finally` เสมอ · timeout ต้องอยู่ในฟังก์ชันเดียวกับที่คืนธง ไม่ใช่ครอบจากข้างนอก · ทุกอย่างที่วาดทับจอระหว่างจับภาพต้องมี `data-capture-hide`

## 4.12 รายงานของเจ้าของยิม และการลบบัญชี (รุ่น `b8a9d96`)

### 4.12.1 endpoint รายงาน

`server/admin-reports.js` · หกเส้นใต้ `/api/admin/reports/*` เปิดเฉพาะ `admin` · **ทุกเส้นเป็นการอ่านล้วน** และ**ไม่เขียนแถว audit** โดยตั้งใจ — บันทึกที่เต็มไปด้วย "มีคนเปิดดูตาราง" คือบันทึกที่ไม่มีใครอ่าน

| กติกา | ค่า |
|---|---|
| เขตเวลาของทุกวันที่ | `date(ts/1000,'unixepoch','+7 hours')` — วันตามเวลากรุงเทพ |
| ช่วงที่ขอได้ | ไม่เกิน **366 วัน** ต่อหนึ่งคำขอ |
| เพดานแถวที่ส่งกลับเป็น JSON | **5,000 แถว** พร้อม `truncated: true` และ `total` เต็ม |
| เพดานของ CSV | **ไม่มี** — `?format=csv` ส่งครบทุกแถวเสมอ |
| รูปแบบ CSV | UTF-8 **พร้อม BOM** · CRLF · เวลา ISO `+07:00` คู่กับวันที่ไทย พ.ศ. · เงินเป็นตัวเลขทศนิยม 2 ตำแหน่ง · เบอร์โทรมีขีด |
| ยอดขายนับจาก | `orders.reviewed_at` เฉพาะ `status='paid' AND manual_grant=0` |
| ประวัติการสแกน อ่านจาก | `check_ins` ทั้งตาราง **ไม่ใช่ `audit_logs`** ซึ่งมีแต่ `checkin.allowed` |

**สามกับดักที่เขียนไว้ในหัวไฟล์ และห้ามลืมเมื่อแก้ต่อ**

1. **แถว `checkin.allowed` ใน `audit_logs` เก็บรหัสแถวเช็คอินไว้ใน `entity_id` ทั้งที่ `entity_type` ยังเป็น `'member'`** — join ตรง ๆ กับ `members` จะไม่เจออะไรเลย
2. **`before_json`/`after_json` ไม่ออกจากไฟล์นี้** สองคอลัมน์นั้นมีชื่อ เบอร์โทร และอีเมลของสมาชิก · รายงานบอกได้แค่ว่า**ช่องไหนถูกแก้** ("แก้: เบอร์โทร, อีเมล") ไม่บอกว่าแก้เป็นอะไร
3. **`check_ins.failure_reason` เป็นข้อความไทยอิสระ ไม่ใช่ enum** — จัดกลุ่มด้วยคำสำคัญเท่านั้น การ `GROUP BY` ตรงตัวจะพังวันที่มีคนแก้คำผิดในข้อความ

**`tests/report-actions.test.js`** อ่าน `server/*.js` หา action ที่เขียนลง `audit_logs` จริง (ปัจจุบัน **42 ตัว**) แล้วบังคับว่าทุกตัวต้องมีคำแปลไทยในตาราง `ACTIONS` — action ที่เพิ่มเดือนหน้าแล้วลืมแปล จะทำให้เทสต์แดง แทนที่จะไปโผล่เป็นรหัสดิบบนหน้าจอเจ้าของยิม

### 4.12.2 `user.login` / `user.logout`

เขียนลง `audit_logs` **เฉพาะตอนล็อกอินสำเร็จ** · `after_json` มีแค่ `{ role }` · **ไม่เก็บหมายเลข IP และไม่เก็บ user agent** · การล็อกอินที่ล้มเหลวไม่ถูกบันทึกเลย (การกันคนสุ่มรหัสใช้ rate limit และการล็อกบัญชีอยู่แล้ว) · แถว `user.logout` มีเฉพาะตอนกดออกเอง session ที่หมดอายุไปเงียบ ๆ ไม่ทิ้งแถว

> เจตนาเชิงนโยบาย: รายงานนี้ตอบว่า**ใครเข้าเวร** ไม่ได้ตอบว่า**เขายืนอยู่ที่ไหน** · ถ้าวันหน้าตัดสินใจเก็บ IP ต้องแก้บทที่ 2 (ประเภทข้อมูลส่วนบุคคล) และกำหนดอายุการเก็บพร้อมกัน · มีเทสต์ที่ยิง regex หา IPv4 และชื่อเบราว์เซอร์ในแถวที่เขียนจริง เพื่อกันของหลุดในอนาคต

### 4.12.3 migration 018 และสิ่งที่มันยังทำไม่ได้

`018_audit_survives_delete` สร้างตาราง `audit_logs` ขึ้นใหม่ (SQLite แก้ foreign key ในที่เดิมไม่ได้) แล้วย้ายข้อมูลเดิมมาทั้งหมด · `actor_id` มี `DEFAULT 'deleted-user'` และ **`ON DELETE SET DEFAULT`** · บัญชีตัวแทน `deleted-user` ถูกสร้างพร้อมกัน: **ไม่มีรหัสผ่าน สถานะ `suspended` ล็อกอินไม่ได้ และถูกซ่อนจาก `GET /api/users` กับดรอปดาวน์ตัวกรองของรายงาน** — มันเป็นปลายทางของ foreign key ไม่ใช่คนที่ทำงานที่นี่ · รายงานแปลงเป็นข้อความ **"บัญชีที่ถูกลบ"**

**ข้อจำกัดที่ยังอยู่ และต้องรู้ก่อนวางแผนลบบัญชี** migration 018 ครอบเฉพาะ `audit_logs` ตารางอื่นยังอ้าง `users` แบบไม่มี `ON DELETE`:

`password_setup_tokens.user_id` · `check_ins.scanned_by` · `orders.reviewed_by` · `problem_reports.reported_by` · `members.user_id`

**ผลจริงในวันนี้คือยังลบบัญชีไหนไม่ได้เลย** เพราะทุกบัญชีที่สร้างผ่านหน้า "บัญชีผู้ใช้" จะมีแถวใน `password_setup_tokens` เสมอ (ระบบออกลิงก์ตั้งรหัสให้พร้อมกับการสร้างบัญชี) — 018 จึงเป็น**เกราะที่เตรียมไว้ล่วงหน้า ยังไม่ใช่ของที่ทำงานอยู่** และตัวที่ติดจริงตัวแรกคือ `password_setup_tokens` **ถ้าจะทำ migration 019 ให้เริ่มที่ตารางนั้น**

> ทางที่ใช้อยู่และปลอดภัยกว่ายังเป็น **ระงับบัญชี** ซึ่งปิดการเข้าใช้ทันทีและเก็บประวัติไว้ครบ (ดูข้อ 2.4)

## ก.2 รายการตรวจตามรอบ

**ทุกสัปดาห์ — เจ้าของยิมหรือผู้ดูแล (5 นาที)**

**สถานะ ณ 20 กันยายน 2569** เครื่องจริงให้บริการอยู่บนรุ่น `856846c` · รุ่น **`b8a9d96`** (รายงานสำหรับเจ้าของยิม และหน้าจัดการบัญชีผู้ใช้) **ผ่าน QA ทั้งฝั่ง API และหน้าจอแล้ว รอขึ้นเครื่อง** · งานเคาน์เตอร์ พอร์ทัลสมาชิก อีเมลของระบบ หน้าจอเนื้อหา และรายงาน ครบทั้งหมด · **เหลือฝั่งเจ้าของยิมสองเรื่องก่อนใช้เต็มรูปแบบ**: กรอกรหัสกล่องจดหมายแล้วกดส่งเมลทดสอบ และตั้งราคาแพ็กเกจที่ยังเป็นร่าง · บัญชีของยิมทั้งสองบัญชีเป็นผู้ดูแลระบบตั้งแต่ 20 ก.ย. 2569

## ก.5 ขอบเขตของเอกสารฉบับนี้
