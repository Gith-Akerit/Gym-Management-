# Gym Management — สุขฤทัย ฟิตเนส

ระบบจัดการยิมสาขาเดียว ประกอบด้วยเว็บแอดมิน แอปสมาชิกแบบ mobile-first และ API เดียวกันที่แอป Expo ใช้

**ส่งมอบครบทั้ง 3 เฟสแล้ว** — สมัครสมาชิกด้วยอีเมล + OTP, จัดการสมาชิก, ตั้งค่าข้อมูลยิมและแพ็กเกจ,
ซื้อแพ็กเกจด้วย PromptPay QR พร้อมอัปโหลดสลิปและให้แอดมินยืนยัน และเช็คอินด้วย QR ให้พนักงานสแกน

## เทคโนโลยีที่ใช้

| ส่วน | เทคโนโลยี | เหตุผล |
|---|---|---|
| API | Node.js 24 + Express 5 | ใช้ `node:sqlite` ที่มากับ Node ได้เลย ไม่ต้องคอมไพล์ native module บน Windows |
| ฐานข้อมูล | SQLite (WAL) | ยิมสาขาเดียว โหลดต่ำ ติดตั้งง่าย สำรองข้อมูลด้วยการคัดลอกไฟล์ ย้ายไป PostgreSQL ได้เมื่อโตขึ้น (ดู `docs/technical-design.md`) |
| เว็บ (แอดมิน + สมาชิก) | React 19 + Vite | หน้าเดียวครอบคลุมทั้งสองบทบาท ลดของที่ต้องดูแล |
| แอปมือถือ | Expo / React Native (`mobile/`) | โค้ดเดียวได้ทั้ง iOS และ Android ใช้ API ชุดเดียวกับเว็บ |
| อีเมล | nodemailer + SMTP | ไม่ผูกกับผู้ให้บริการรายใดรายหนึ่ง |

## เริ่มใช้งานบนเครื่องพัฒนา

ต้องมี Node.js 24 ขึ้นไป

```bash
npm install
cp .env.example .env
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"   # ใส่ค่าลง OTP_SECRET

npm run db:migrate        # สร้างตาราง
npm run db:seed           # ข้อมูลยิมและแพ็กเกจร่าง (รันซ้ำได้ ไม่ทับของที่แก้ไว้)
ADMIN_EMAIL=you@example.com npm run db:admin   # ตั้งบัญชีผู้ดูแลระบบ

npm start                 # API ที่ http://127.0.0.1:3000
npm run dev               # เว็บที่ http://localhost:5173 (proxy ไป API)
```

ระหว่างพัฒนาให้รัน SMTP ปลอมไว้รับอีเมล OTP เช่น `npx maildev --smtp 1025 --web 1080` แล้วเปิด http://localhost:1080

## ค่าคอนฟิก

ทุกค่าอ่านจาก environment ไม่มีค่าใดฝังอยู่ในโค้ด ดูรายการเต็มใน `.env.example`

| ตัวแปร | จำเป็น | หมายเหตุ |
|---|---|---|
| `OTP_SECRET` | ใช่ | อย่างน้อย 32 ตัวอักษร ใช้เซ็นรหัส OTP และ rate-limit bucket เปลี่ยนค่านี้แล้วรหัสที่ค้างอยู่จะใช้ไม่ได้ |
| `APP_ORIGIN` | ใช่ | ที่อยู่เว็บ บน production ต้องเป็น `https://` ระบบจะปฏิเสธถ้าไม่ใช่ |
| `TRUST_PROXY` | ใช่ (production) | จำนวน reverse proxy ที่คั่นอยู่ ค่าเริ่มต้น `1` **ตั้งผิดแล้วสมาชิกทั้งยิมจะใช้โควตาขอรหัส OTP ร่วมกันก้อนเดียว** ดูหัวข้อถัดไป |
| `DATABASE_PATH` | ไม่ | ค่าเริ่มต้น `./data/gym.sqlite` |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` / `SMTP_PASSWORD` / `MAIL_FROM` | ใช่ | บน production ต้องมี user/password และใช้ TLS |
| `ADMIN_EMAIL` | เฉพาะตอนตั้งแอดมิน | ไม่มี API ใดเลื่อนสิทธิ์เป็นแอดมินได้ |
| `PROMPTPAY_ID` | ใช่ (Phase 2) | บัญชีที่รับเงิน: เบอร์มือถือไทย, เลขบัตรประชาชน 13 หลัก หรือ e-Wallet ID 15 หลัก เป็นข้อมูลส่วนตัวของเจ้าของ อย่าใส่ไว้ในโค้ด |
| `SLIP_STORAGE_PATH` | ไม่ | ที่เก็บรูปสลิป ค่าเริ่มต้น `./data/slips` **ต้องไม่อยู่ในโฟลเดอร์ที่เสิร์ฟเป็นไฟล์สาธารณะ** |
| `SLIP_RETENTION_DAYS` | ไม่ | ระยะเวลาเก็บรูปสลิป ค่าเริ่มต้น 365 วัน ใช้โดย `npm run slips:prune` |

**ข้อมูลธุรกิจ เช่น เวลาเปิดทำการ เบอร์โทร ที่อยู่ ราคาแพ็กเกจ ข้อความแจ้งเวลาตรวจสลิป และเวลาที่ให้ชำระเงินต่อคำสั่งซื้อ ไม่ได้อยู่ใน environment**
— แก้ในหน้าแอดมิน (แท็บ “ข้อมูลยิม” และ “แพ็กเกจ”)

## การชำระเงินด้วย PromptPay (Phase 2)

ยิมรับเงินเข้าบัญชีตัวเองโดยตรง ไม่ผ่านผู้ให้บริการชำระเงิน จึงไม่มีค่าธรรมเนียม แต่ก็ไม่มีใครมายืนยันให้อัตโนมัติ
ขั้นตอนจริงคือ **สมาชิกสแกน QR โอนเงิน → อัปโหลดสลิป → แอดมินตรวจกับแอปธนาคารแล้วกดอนุมัติ → ระบบสร้างสิทธิ์ให้**

- **หน่วยของราคาใน API**: `price_thb` คือบาท (ใส่ทศนิยมได้ 2 ตำแหน่ง) `price_satang` คือสตางค์ (จำนวนเต็ม)
  ส่งได้ทางเดียวต่อหนึ่งคำขอ อ่านค่าจาก API แล้วเขียนกลับโดยไม่แก้อะไร ราคาต้องไม่เปลี่ยน
- **แพ็กเกจราคา 0 บาท** ข้ามขั้นตอน QR และสลิปทั้งหมด คำสั่งซื้อเข้าคิวให้แอดมินกดมอบสิทธิ์โดยตรง
- ระบบสร้าง QR ตามมาตรฐาน EMVCo เอง จาก `PROMPTPAY_ID` และยอดของคำสั่งซื้อ รองรับทั้งเบอร์โทร เลขบัตรประชาชน และ e-Wallet ID
- **สิทธิ์ไม่ได้เกิดทันทีที่โอน** หน้าจอสมาชิกบอกเรื่องนี้ตรง ๆ และแสดงข้อความว่าจะตรวจสลิปเมื่อไร ซึ่งแอดมินแก้ได้เอง (ค่าเริ่มต้น “ภายใน 30 นาทีในเวลาทำการ”)
- ปุ่มอนุมัติกดไม่ได้จนกว่าแอดมินจะติ๊กว่าตรวจกับแอปธนาคารแล้ว เพราะไม่มีหลักฐานจากบุคคลที่สามมายืนยันแทน
- ระบบเตือนเมื่อยอดที่สมาชิกแจ้งไม่ตรงกับราคา และเมื่อรูปสลิปหรือเลขอ้างอิงเคยถูกใช้กับคำสั่งซื้ออื่นแล้ว
- อนุมัติผิดยกเลิกได้ ระบบจะเพิกถอนสิทธิ์และบันทึกทั้งสองครั้งไว้ในประวัติ

### สลิปเป็นข้อมูลส่วนบุคคล — นโยบายการเก็บและการลบ

สลิปมีชื่อผู้โอน บางส่วนของเลขบัญชี ยอดเงินและเวลา ถือเป็นข้อมูลส่วนบุคคลตาม PDPA

| หัวข้อ | นโยบาย |
|---|---|
| เก็บที่ไหน | โฟลเดอร์ตาม `SLIP_STORAGE_PATH` (ค่าเริ่มต้น `./data/slips`) **อยู่นอก web root** ไม่ถูกเสิร์ฟเป็นไฟล์สาธารณะ |
| ชื่อไฟล์ | เซิร์ฟเวอร์ตั้งเองเป็น UUID ไม่เคยใช้ชื่อไฟล์ที่เบราว์เซอร์ส่งมา |
| ใครเปิดดูได้ | ผู้ดูแลระบบ และเจ้าของสลิปคนนั้นเท่านั้น ผ่าน endpoint ที่ตรวจสิทธิ์ ไม่มี URL ที่เดาได้ |
| เก็บนานแค่ไหน | **1 ปี** นับจากวันที่อัปโหลด (`SLIP_RETENTION_DAYS` ปรับได้) เก็บไว้เพื่อกระทบยอดย้อนหลังและตอบข้อโต้แย้งของลูกค้า |
| ลบอย่างไร | `npm run slips:prune` ลบทั้งไฟล์และแถวในฐานข้อมูล ดูก่อนลบด้วย `npm run slips:prune -- --dry-run` |
| ข้อมูลอื่นที่เกี่ยวข้อง | EXIF และ XMP ถูกถอดทิ้งตั้งแต่ตอนอัปโหลด จึงไม่มีพิกัด GPS ของลูกค้าเก็บอยู่ |

ตั้ง `npm run slips:prune` ให้รันอัตโนมัติเดือนละครั้ง (Task Scheduler บน Windows หรือ cron บน Linux)
คำสั่งนี้ลบเฉพาะรูปสลิป **คำสั่งซื้อ ยอดเงิน และ audit log ยังอยู่ครบ** จึงยังกระทบยอดย้อนหลังได้

### ตั้ง `TRUST_PROXY` ให้ถูก

บน production ระบบบังคับ HTTPS จึงต้องมี reverse proxy หรือ Cloudflare คั่นเสมอ ถ้าไม่บอกแอปว่ามี proxy กี่ชั้น
ทุกคำขอจะดูเหมือนมาจาก IP เดียวกันคือตัว proxy เอง แล้ว **สมาชิกทั้งยิมจะใช้โควตาขอรหัส OTP ต่อ IP ร่วมกันก้อนเดียว**
ช่วงเย็นที่คนเข้าพร้อมกัน สมาชิกจะถูกปฏิเสธทั้งที่ไม่ได้ทำอะไรผิด และคนภายนอกคนเดียวก็ปิดทางล็อกอินของทุกคนได้

| ติดตั้งแบบไหน | ค่าที่ตั้ง |
|---|---|
| nginx / Caddy ตัวเดียวหน้าแอป | `TRUST_PROXY=1` |
| Cloudflare → nginx → แอป | `TRUST_PROXY=2` |
| แอปรับคำขอตรงจากอินเทอร์เน็ต (ไม่แนะนำ) | `TRUST_PROXY=0` |

ตรวจว่าตั้งถูกได้จาก log ของ proxy เทียบกับพฤติกรรม rate limit หรือชั่วคราวให้ยิงจากเครื่องต่าง ๆ แล้วดูว่าไม่ถูกปฏิเสธ
ตั้งค่าเกินจำนวน hop จริงจะเปิดช่องให้ผู้ใช้ปลอม `X-Forwarded-For` เพื่อเลี่ยงเพดานต่อ IP ได้
(เพดานต่ออีเมล 5 ครั้ง/15 นาที กับ cooldown 60 วินาที ยังทำงานอยู่และเป็นด่านกันสแปมหลัก)

## ทำให้อีเมล OTP ไม่ตกถังขยะ (SPF / DKIM / DMARC)

ถ้าอีเมล OTP ตกโฟลเดอร์สแปม สมาชิกจะสมัครไม่ได้เลย ต้องตั้งค่าทั้งสามอย่างนี้ **ก่อน** เปิดให้คนทั่วไปใช้

สมมติว่าโดเมนที่ส่งคือ `suklutaifitness.com` และใช้ผู้ให้บริการส่งอีเมล (เช่น Amazon SES, SendGrid, Mailgun, Google Workspace)

**1. SPF** — ประกาศว่าเซิร์ฟเวอร์ใดส่งแทนโดเมนเราได้ ใส่ TXT record เดียวที่ root ของโดเมน

```
ชื่อ:  @            (คือ suklutaifitness.com)
ชนิด:  TXT
ค่า:   v=spf1 include:<ค่าที่ผู้ให้บริการกำหนด> -all
```

ห้ามมี SPF record มากกว่า 1 รายการต่อโดเมน ถ้าส่งจากหลายที่ให้รวม `include:` ไว้ในบรรทัดเดียว
`-all` คือปฏิเสธผู้ส่งอื่นทั้งหมด ระหว่างทดสอบใช้ `~all` ก่อนได้ แล้วเปลี่ยนเป็น `-all` เมื่อมั่นใจ

**2. DKIM** — เซ็นอีเมลด้วยกุญแจของโดเมน ผู้ให้บริการจะให้ selector กับ public key มา

```
ชื่อ:  <selector>._domainkey        (เช่น s1._domainkey)
ชนิด:  TXT  หรือ CNAME ตามที่ผู้ให้บริการกำหนด
ค่า:   v=DKIM1; k=rsa; p=<public key ที่ได้รับ>
```

ผู้ให้บริการบางรายให้ใส่ CNAME 3 รายการแทน ให้ทำตามหน้าตั้งค่าของรายนั้น แล้วรอจนสถานะขึ้นว่า verified

**3. DMARC** — บอกผู้รับว่าจะทำอย่างไรเมื่อ SPF/DKIM ไม่ผ่าน และส่งรายงานกลับมาให้เรา

```
ชื่อ:  _dmarc
ชนิด:  TXT
ค่า:   v=DMARC1; p=none; rua=mailto:dmarc@suklutaifitness.com; fo=1; pct=100
```

เริ่มด้วย `p=none` เพื่อเก็บรายงานก่อน ประมาณ 2 สัปดาห์ เมื่อเห็นว่าอีเมลของเราผ่านทั้ง SPF และ DKIM แล้วค่อยเปลี่ยนเป็น `p=quarantine` และ `p=reject`

**4. ให้ `MAIL_FROM` อยู่บนโดเมนเดียวกับที่เซ็น DKIM** — เช่น `ยิมสุขฤทัย <noreply@suklutaifitness.com>`
ถ้า `MAIL_FROM` เป็นคนละโดเมนกับที่เซ็น DMARC จะไม่ผ่านแม้ SPF และ DKIM จะถูกต้อง

**5. ตรวจก่อนเปิดใช้จริง**

- ส่งอีเมลทดสอบไปที่ https://www.mail-tester.com แล้วดูให้ได้คะแนน 9/10 ขึ้นไป
- ทดสอบกับ Gmail, Outlook และโดเมนของบริษัทอย่างละ 1 บัญชี ว่าเข้ากล่องหลักภายใน 30 วินาที (เคส MEM-051 ของ QA)
- อย่าใช้อีเมลฟรี เช่น `@gmail.com` เป็นผู้ส่ง เพราะ DMARC ของ Gmail จะทำให้ถูกปฏิเสธ

## โหมดทดลอง (Pilot Mode)

`PILOT_MODE=1` ทำให้ระบบขึ้นได้โดยไม่ต้องมี PromptPay ID และไม่ต้องมีบริการส่งอีเมล

- **รหัส OTP แสดงในหน้าแอดมิน** แทนการส่งอีเมล (แท็บ "รหัส OTP" และในหน้าสมาชิกรายคน)
  รหัสเก็บในหน่วยความจำเท่านั้น ไม่ลงฐานข้อมูล และเห็นได้เฉพาะ `admin`
- **ไม่มีหน้าซื้อแพ็กเกจ** แอดมินกด "มอบแพ็กเกจ" ให้สมาชิกจากหน้าสมาชิกรายคน พร้อมระบุเหตุผลที่บังคับกรอก
  คำสั่งซื้อที่ได้ถูกทำเครื่องหมาย `manual_grant` และ**ไม่ถูกนับเป็นรายได้**ในสรุปยอดขาย
- **ส่วนอื่นใช้ได้ครบ** สมัครสมาชิก จัดการสมาชิก ตั้งค่าแพ็กเกจ QR เช็คอิน นับจำนวนครั้ง และรายการที่ใกล้หมดอายุ
- **แถบเตือน "โหมดทดลอง"** อยู่บนทุกหน้าของแอดมินและพนักงาน
- **ล็อกอินครั้งแรกของแอดมิน** ใช้ `npm --silent run pilot:code -- <อีเมล>` บนเซิร์ฟเวอร์
  สร้าง challenge ใหม่แล้วพิมพ์รหัสกับลิงก์ใช้ครั้งเดียวออกมา ทำงานเฉพาะเมื่อ `PILOT_MODE=1`
  และเฉพาะบัญชีที่เป็น `admin` แล้วเท่านั้น พร้อมบันทึก audit ว่ารหัสถูกออกจาก CLI
- **ปิดแล้วกลับเป็นปกติทันที** ข้อมูลที่เกิดตอนเปิดโหมดทดลองใช้ต่อได้ทั้งหมด ไม่ต้องติดตั้งใหม่

ขั้นตอนเปิด-ปิดอยู่ใน [docs/deploy.md](docs/deploy.md)

## การเช็คอินด้วย QR (Phase 3)

สมาชิกเปิดแอปแล้วเห็น QR บนหน้าแรกทันที ไม่ต้องกดอะไร ยื่นจอให้พนักงานสแกนที่เคาน์เตอร์

- **QR เปลี่ยนเองทุกนาทีและใช้ได้ครั้งเดียว** ข้างในมีแค่รหัสสุ่มกับลายเซ็น ไม่มีชื่อ ไม่มีรหัสสมาชิก
  ภาพหน้าจอที่ส่งให้เพื่อนจึงใช้เข้ายิมไม่ได้ และการขอรหัสใหม่จะยกเลิกรหัสก่อนหน้าทันที
- **ตรวจอายุด้วยนาฬิกาของเซิร์ฟเวอร์** เครื่องสมาชิกที่ตั้งเวลาผิดจึงไม่เสียสิทธิ์และไม่ได้เปรียบ
- **สถานะสมาชิกมาก่อนแพ็กเกจ** สมาชิกที่ถูกระงับเข้าไม่ได้แม้แพ็กเกจยังไม่หมดอายุ
- **หักโควตาแบบ atomic** และหักจากแพ็กเกจที่หมดอายุเร็วที่สุดก่อน จำนวนครั้งคงเหลือติดลบไม่ได้
- **สแกนซ้ำภายในเวลาที่ตั้งไว้ถือเป็นครั้งเดิม** ไม่หักสิทธิ์ซ้ำ (ค่าเริ่มต้น 5 นาที แก้ได้ในหน้าแอดมิน)
- **รายการที่ถูกปฏิเสธถูกบันทึกพร้อมเหตุผล** เพราะเป็นเคสที่มีคนมาถามย้อนหลังเสมอ
- **QR ที่ระบุตัวสมาชิกไม่ได้แยกไปอีกแท็บ** หน้าประวัติของแอดมินเปิดมาที่ “รายชื่อสมาชิก”
  ส่วนการสแกน QR ปลอมหรืออ่านไม่ออกอยู่ในแท็บ “QR ไม่ถูกต้อง” พร้อมจำนวนรายการ
  ทุกอย่างยังถูกบันทึกครบ และ `GET /api/check-ins` ที่ไม่ระบุ `scope` ยังคืนทั้งหมดเหมือนเดิม
- **ขอ QR ใหม่ได้ 120 ครั้งต่อ 15 นาทีต่อบัญชี** พอสำหรับเปิดหน้าจอทิ้งไว้ราว 2 ชั่วโมง
  และกันไม่ให้บัญชีเดียวเขียนตารางรัว ๆ
- **โทเคนเช็คอินเก็บไว้ 7 วันแล้วถูกกวาดทิ้ง** ตัวกวาดใน `createApp` ทำงานทุกนาที
  ประวัติการเข้าใช้บริการเก็บที่ตาราง `check_ins` จึงไม่หายไปด้วย

**หน้าสแกนของพนักงาน** สแกนได้ 2 ทาง เลือกทางใดทางหนึ่งหรือใช้พร้อมกันก็ได้

1. **กล้องของแท็บเล็ต** ติ๊ก “ใช้กล้องของเครื่องนี้สแกน” แล้วหันกล้องไปที่จอของสมาชิก ระบบอ่านให้เอง
   ใช้ `BarcodeDetector` ของเบราว์เซอร์เมื่อมี (Chrome/Edge บน Android และเดสก์ท็อป) ถ้าไม่มีจะโหลดตัวถอดรหัส JS มาใช้แทน
   ตัวเลือกนี้จำไว้ต่อเครื่อง และคืนกล้องให้ระบบทันทีที่ติ๊กออก
2. **เครื่องอ่าน QR แบบ USB/Bluetooth** ที่เสียบกับแท็บเล็ตหรือคอมหน้าเคาน์เตอร์ จะพิมพ์รหัสลงช่องแล้วกด Enter ให้เอง
   ช่องกรอกจึงโฟกัสไว้ตลอดแม้เปิดกล้องอยู่

ผลลัพธ์แสดงเป็นแผ่นใหญ่ มีทั้งสี ไอคอน และข้อความ อ่านจากระยะประมาณ 1 เมตรได้

**ต้องเปิดผ่าน HTTPS** เบราว์เซอร์ไม่ยอมให้เว็บใช้กล้องบน `http://` ยกเว้น `localhost`
ซึ่งตรงกับที่ระบบบังคับ HTTPS บน production อยู่แล้ว

**สิทธิ์ของ role `staff`**: สแกนเช็คอิน ดูประวัติเช็คอิน และดูคิวสลิปแบบอ่านอย่างเดียว
การอนุมัติสลิปและการจัดการสมาชิกยังเป็นสิทธิ์ของ `admin` เท่านั้น

## บัญชีผู้ใช้และสิทธิ์

เมนูผู้ดูแลระบบ: **สมาชิก · ผู้ใช้และสิทธิ์ · ตรวจสลิป (หรือ รหัส OTP ในโหมดทดลอง) · สแกนเช็คอิน · เช็คอิน · แพ็กเกจ · ข้อมูลยิม**

| สิทธิ์ | ทำอะไรได้ |
|---|---|
| `member` | แอปสมาชิก: ซื้อแพ็กเกจ ส่งสลิป QR เช็คอิน ดูสิทธิ์และประวัติของตัวเอง |
| `staff` | สแกนเช็คอิน ดูประวัติเช็คอิน และดูคิวสลิปแบบอ่านอย่างเดียว |
| `admin` | ทุกอย่าง รวมถึงสแกนเช็คอินเองได้ เพราะยิมเล็ก ๆ เจ้าของมักยืนเคาน์เตอร์เอง |

- **สร้างบัญชีพนักงานหรือผู้ดูแลระบบ** ที่หน้า "ผู้ใช้และสิทธิ์" ด้วยอีเมลอย่างเดียว ไม่มีรหัสผ่านให้ตั้ง
  เจ้าของอีเมลเข้าระบบด้วยรหัส OTP เหมือนทุกบัญชี ส่วนบัญชีสมาชิกเกิดจากการสมัครเองหรือหน้า "สมาชิก"
- **เปลี่ยนสิทธิ์ได้ทั้งสองทาง** member ⇄ staff ⇄ admin ทุกครั้งเข้า audit log พร้อมว่าใครเป็นคนเปลี่ยน
- **การลดสิทธิ์หรือระงับบัญชีจะตัด session ทันที** ไม่ต้องรอ token หมดอายุ คนที่ถูกลดสิทธิ์จึงไม่ค้างอยู่บนหน้าจอที่ตัวเองไม่มีสิทธิ์แล้ว
- **ระบบไม่ยอมให้เหลือ 0 ผู้ดูแลระบบ** ลดสิทธิ์หรือระงับผู้ดูแลระบบคนสุดท้ายที่ใช้งานได้จะถูกปฏิเสธด้วย 409
- **ระงับบัญชี ≠ ระงับสมาชิกภาพ** อันแรกคือห้ามเข้าสู่ระบบ (`users.status`) อันหลังคือสถานะสมาชิกที่หน้า "สมาชิก" (`members.status`)

## ความปลอดภัยที่ทำไว้แล้วใน Phase 1

- รหัส OTP 6 หลัก อายุ 5 นาที ใช้ได้ครั้งเดียว เก็บเป็น HMAC ไม่เก็บตัวรหัส และไม่ปรากฏใน log หรือ response ใด ๆ
- ขอรหัสได้ทุก 60 วินาที จำกัด 5 ครั้ง/อีเมล และ 40 ครั้ง/IP ต่อ 15 นาที (IP ของผู้ใช้จริง ไม่ใช่ของ proxy — ดู `TRUST_PROXY`)
- **กรอกรหัสผิด 5 ครั้ง ล็อกอีเมลนั้น 15 นาที** นับข้ามคำขอ ไม่ใช่นับเฉพาะภายในคำขอเดียว
- ขอรหัสด้วยอีเมลที่ไม่มีในระบบได้ผลลัพธ์เหมือนอีเมลที่มีอยู่ เพื่อไม่ให้ใช้ไล่เก็บรายชื่อลูกค้า
- session token สุ่ม 256 บิต เก็บเป็น hash ฝั่งเซิร์ฟเวอร์ เว็บใช้ cookie แบบ HttpOnly + SameSite=Strict มือถือใช้ bearer token
- ตรวจสิทธิ์ที่ฝั่งเซิร์ฟเวอร์ทุก endpoint ไม่ได้อาศัยการซ่อนปุ่มใน UI
- ทุกคำสั่งเขียนข้อมูลที่ไม่ใช่ GET ต้องมี header `X-Gym-Client` และตรวจ Origin เพื่อกัน CSRF
- query ใช้ parameter ทั้งหมด ข้อความที่ผู้ใช้กรอกถูกแสดงเป็นข้อความเสมอ
- ข้อความ error ที่ส่งออกไม่มีรายละเอียดภายในหรือ stack trace และเป็นภาษาไทยทุกข้อความ รวมถึงกรณีที่ไม่ได้เขียนข้อความไว้เอง
- เมื่อเกิดข้อผิดพลาดที่ไม่คาดคิด ผู้ใช้จะได้รหัสอ้างอิงเดียวกับที่บันทึกไว้ใน log เพื่อใช้แจ้งปัญหา

## นำขึ้นใช้งานจริง

ขั้นตอนเต็มสำหรับขึ้นอินเทอร์เน็ต (Docker + Caddy, PM2 + nginx, Fly.io, Render), เช็กลิสต์ค่า env,
การตั้งอีเมล OTP ด้วย Brevo และรายการตรวจหลัง deploy อยู่ใน [docs/deploy.md](docs/deploy.md)
ส่วนย่อด้านล่างคือสิ่งที่ทุกวิธีมีเหมือนกัน

1. ตั้ง `NODE_ENV=production`, `APP_ORIGIN=https://...`, `OTP_SECRET` และค่า SMTP ที่มีการยืนยันตัวตน
2. `npm ci && npm run build`
3. `npm run db:migrate && npm run db:seed`
4. `ADMIN_EMAIL=... npm run db:admin`
5. รัน `npm start` หลัง reverse proxy ที่ทำ HTTPS ให้ (เช่น Caddy หรือ Nginx)
6. ตั้ง `TRUST_PROXY` ให้ตรงกับจำนวน proxy จริง (ดูหัวข้อด้านบน)
7. **สำรองข้อมูล**: หยุดบริการชั่วครู่แล้วคัดลอก `data/gym.sqlite*` ทั้งสามไฟล์ (รวม `-wal` และ `-shm`) หรือใช้ `sqlite3 data/gym.sqlite ".backup out.sqlite"` ขณะรันอยู่ได้ ควรตั้งให้ทำอัตโนมัติทุกวันและทดสอบกู้คืนอย่างน้อยหนึ่งครั้งก่อนเปิดใช้จริง

## แผนย้อนกลับเมื่อ deploy แล้วมีปัญหา (rollback plan)

**สำรองไฟล์ฐานข้อมูลก่อนทุกครั้งที่ deploy** ขั้นตอนกู้คืนแบ่งตามความรุนแรง

**กรณีที่ 1 — โค้ดใหม่มีปัญหา แต่โครงสร้างฐานข้อมูลไม่เปลี่ยน (พบบ่อยที่สุด)**

```bash
git checkout <commit เดิมที่ใช้งานได้>
npm ci && npm run build
# เริ่มบริการใหม่ ไม่ต้องแตะฐานข้อมูล
```

**กรณีที่ 2 — deploy มี migration ใหม่และต้องย้อนโครงสร้าง**

```bash
# 1. หยุดบริการก่อน
# 2. สำรองไฟล์ให้ครบทั้งสามไฟล์
cp data/gym.sqlite data/gym.sqlite.bak
cp data/gym.sqlite-wal data/gym.sqlite-wal.bak 2>/dev/null || true
cp data/gym.sqlite-shm data/gym.sqlite-shm.bak 2>/dev/null || true
# 3. ย้อน migration ล่าสุดหนึ่งขั้น
ALLOW_DESTRUCTIVE_ROLLBACK=yes npm run db:rollback
# 4. กลับไปใช้โค้ดเวอร์ชันเดิมแล้วเริ่มบริการ
```

**สิ่งที่ต้องรู้ก่อนกด rollback**

- ข้อมูล**สมาชิกและ audit log ไม่หาย** เพราะอยู่ใน migration 001 ซึ่งไม่ถูกย้อน
- แต่การย้อน migration 002 จะ **ลบตาราง `gym_profile`, `gym_hours` และ `packages` ทิ้งทั้งหมด**
  เวลาเปิดทำการ เบอร์โทร และ **ราคาแพ็กเกจที่เจ้าของยิมกรอกไว้เองจะหายไปด้วย**
- หลังย้อนแล้วจะ migrate กลับขึ้นมาใหม่ ต้องรัน `npm run db:seed` เพื่อสร้างค่าเริ่มต้น
  แล้ว **กรอกราคาและเวลาเปิดทำการใหม่ด้วยมือ** หรือกู้จากไฟล์สำรองแทน
- ด้วยเหตุนี้ ทางที่ปลอดภัยกว่าเกือบเสมอคือ **กู้จากไฟล์สำรอง** ไม่ใช่ `db:rollback`

**กู้จากไฟล์สำรอง**

```bash
# หยุดบริการก่อน แล้วค่อยเอาไฟล์กลับ
cp data/gym.sqlite.bak data/gym.sqlite
rm -f data/gym.sqlite-wal data/gym.sqlite-shm   # ทิ้ง WAL ที่ค้างจากเวอร์ชันใหม่
npm run db:migrate                               # ไม่ทำอะไรถ้าโครงสร้างตรงอยู่แล้ว
```

ควรซ้อมขั้นตอนนี้อย่างน้อยหนึ่งรอบบนเครื่องทดสอบก่อนเปิดใช้จริง

## แอปมือถือ (`mobile/`)

```bash
cd mobile && npm install
```

## สิ่งที่ยังไม่ได้ทำและข้อจำกัดที่ทราบ

- **ยังไม่ได้ทดสอบสแกนด้วยกล้องของแท็บเล็ตจริง** โค้ดเปิดกล้องและอ่าน QR ทำเสร็จแล้ว และทดสอบด้วยกล้องจำลองของ Chromium
  ว่าขอสิทธิ์ เปิดสตรีม และคืนกล้องถูกต้อง แต่กล้องจำลองแสดงภาพลายทดสอบ ไม่ใช่ QR จริง
  **จึงยังไม่ได้ยืนยันว่าอ่าน QR จากจอมือถือจริงได้** ก่อนเปิดใช้ต้องลองกับแท็บเล็ตที่จะใช้จริงอย่างน้อย 1 เครื่อง
- **ยังไม่ได้ทดสอบกับจอที่มืดมากหรือกล้องคุณภาพต่ำ** QR แสดงที่ 240 px และหน้าจอแนะนำให้เปิดความสว่างสุด
  แต่เว็บสั่งเพิ่มความสว่างให้เองไม่ได้ ถ้าพบปัญหาหน้างานอาจต้องทำเป็นแอปเนทีฟ
- **ยังไม่ได้สแกน QR ด้วยแอปธนาคารจริง** เพราะจะเกิดการโอนเงินจริงเข้าบัญชียิม ที่ทดสอบแล้วคือโครงสร้าง payload ตาม EMVCo, ยอดในแท็ก 54 และ CRC เทียบกับค่าตรวจสอบมาตรฐานของ CRC-16/CCITT-FALSE ทั้งหมดเป็นการตรวจแบบ offline
  ก่อนเปิดใช้จริง ควรให้เจ้าของยิมสแกนทดสอบด้วยยอดเล็ก เช่น 1 บาท อย่างน้อย 1 ธนาคาร
- **ไฟล์ HEIC จาก iPhone อัปโหลดไม่ได้** ระบบปฏิเสธพร้อมบอกวิธีแก้ เพราะเบราว์เซอร์ของแอดมิน (Chrome/Edge) เปิดดู HEIC ไม่ได้ ซึ่งจะทำให้ตรวจสลิปไม่ได้เลย
  ในทางปฏิบัติ iOS จะแปลงเป็น JPG ให้อัตโนมัติเมื่อเลือกไฟล์ผ่านปุ่มอัปโหลด เพราะฟอร์มประกาศรับเฉพาะ JPG/PNG/WEBP
- **คำสั่งซื้อที่รอตรวจสอบจะไม่หมดอายุเอง** ตั้งใจให้เป็นแบบนี้ เพราะสมาชิกจ่ายเงินไปแล้ว ระบบจึงเรียงคิวจากที่รอนานสุดก่อนและแสดงจำนวนที่ค้าง แทนการยกเลิกอัตโนมัติ
- **แอป Expo ยังไม่ได้ build หรือทดสอบบนเครื่องจริง** เพราะเครื่องที่พัฒนาไม่มี Android SDK / Xcode โค้ดเรียก API ชุดเดียวกับเว็บและแก้ให้ตรงกับ API แล้ว แต่ยังไม่ได้ยืนยันด้วยการรันจริง
- **ชุดสีเป็นของชั่วคราว** ตาม UI reference v0.1 รอไฟล์โลโก้และภาพแบรนด์จริงจากยิม
- ข้อมูลยิมที่ seed มาจาก public directory **ยังไม่ได้รับการยืนยันจากเจ้าของ** เวลาเปิดทำการจึงถูกทำเครื่องหมายว่ายังไม่ยืนยัน และแอปสมาชิกจะเตือนให้โทรสอบถามก่อนเดินทาง
- ราคาแพ็กเกจทั้งหมดเป็น `NULL` จนกว่าเจ้าของยิมจะกรอกเอง แพ็กเกจที่ยังไม่มีราคาจะเปิดขายไม่ได้
- ไม่มีระบบจองคลาสหรือตารางเทรนเนอร์ และไม่มีแนวคิดเรื่องสาขา ตามขอบเขตที่ตกลงไว้
